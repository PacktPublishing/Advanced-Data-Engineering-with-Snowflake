# Chapter 17 clean room runbook

This is an interactive CoCo exercise against the installed Collaboration API.
SQL and YAML generated by CoCo require inspection against the linked Snowflake
reference. There is no claim that the generated configuration has been run here.
Use only the synthetic fixtures and record query IDs and observed output.

1. Run `chapter17_5_cleanroom_fixture.sql` in each account, choosing offset 0
   for TechFlow and 40 for the partner. Confirm 60 distinct hashes in each.
2. Start `cortex` with the intended configured account connection. Read the
   account identity before any write. Send the inventory prompt below.

```text
Inspect the installed Data Clean Rooms API version and my role's
privileges for DCR_DB.PRIVATE.CUSTOMERS. Use metadata only.
Use the current REGISTRY and COLLABORATION APIs. Report missing
privileges and the procedures needed to register a template-only
data offering. Do not change objects or read customer rows.
```

Expected: metadata, API version, missing privileges, proposed registration path.
The object owner supplies only the privileges documented for the installed
REGISTRY and COLLABORATION procedures. Recheck before registration.

3. Ask CoCo to generate a data offering with api_version 2.0.0, spec_type
   data_offering, version v1, dataset object DCR_DB.PRIVATE.CUSTOMERS,
   object_class custom, allowed_analyses template_only, and hashed_email
   category join_standard / column_type hashed_email_b64_encoded. Inspect,
   register, and record the returned ID separately in each account.
4. Send the following prompt in TechFlow's owner session, supplying the
   recorded organization.account identifiers and offering IDs.

```text
Prepare an overlap template and collaboration for the two registered
synthetic offerings. Only the TechFlow account may run the analysis.
The partner contributes data and cannot run this template.
Return one distinct overlap count only when it is at least 10.
Permit no raw identifiers, free-form SQL, activation, or exports.
Use the documented p and p1 aliases and enforce the offering policies.
Show the SQL, YAML, account identifiers, offering IDs, template ID,
and permission matrix before executing anything. Keep approval on.
```

Expected: template SQL and YAML plus the collaboration specification. Check:

- TechFlow is the owner and the only analysis runner.
- The partner only supplies its selected offering to TechFlow.
- COUNT DISTINCT is applied to the matching identity with a fixed HAVING
  threshold of 10. Neither identity values nor arbitrary predicates are outputs.
- Standard table aliases and documented Jinja policy filters are used.
- Both offerings enforce template_only, and no activation destination exists.
- Template updates retain explicit partner approval.

5. Approve only the reviewed template registration and collaboration
   initialization. Use DCR_WH. Record returned identifiers. Poll GET_STATUS
   until owner JOINED. Do not infer completion from a successful submission.
6. In the partner session review the named collaboration and its owner account,
   join, wait for JOINED, and link the partner offering to TechFlow alone.
7. In TechFlow, list offerings/templates. Map the returned TEMPLATE_VIEW_NAME
   values to the template in COLLABORATION.RUN. Expect overlap 20 only.
8. Attempt the template in the partner session: expected denial. Attempt an
   unapproved raw-identifier projection through the collaboration: expected
   denial. Do not test with direct queries by the fixture-owning SYSADMIN role.
9. Repeat registration and initialization under distinct names using
   SMALL_CUSTOMERS in both accounts. Both lists contain the same five hashes.
   The same reviewed template must suppress the aggregate, not return 5 or
   relabel the response as zero. Record the observed suppression representation.
10. Retain specs, template SQL, account/role/warehouse, API version, timestamps,
    query IDs, positive result, negative errors, and suppression evidence.
11. Review teardown against the API reference. TEARDOWN can require a call,
    polling until LOCAL_DROP_PENDING, then another TEARDOWN call. Confirm the
    actual status transitions. Retire registry entries separately; teardown
    does not delete them. Only then remove the synthetic fixture objects.

The share audit prompt for section 2.2 lives in `chapter17_2_coco_share_audit.md`.
